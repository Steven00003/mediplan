# AGENTS.md

Flutter (Dart) + Firebase medication app. Two UX flows (caregiver/doctor in `lib/screens/doctor/`, patient in `lib/screens/paciente/`). 100% client + Firestore rules — no Cloud Functions, no FCM, no Storage. `flutter analyze` clean; 77 tests pass.

## Commands (run from `mediplan/`)

- `flutter pub get` — install deps
- `flutter analyze` — correctness gate (~45s warm, ~150s typical; cold ~300s). Don't kill it.
- `flutter test` — 7 files / 77 tests (~30s). For a single file: `flutter test test/<file>.dart`. Use ASCII `--plain-name` substring for accented names (e.g. `flutter test --plain-name "formato de c"`).
- `flutter build apk` — needs NDK `flutter.ndkVersion` (28.2.13676358 on 3.47.2). SDK/NDK/AGP/Kotlin/Gradle/Java follow Flutter defaults (see `android/app/build.gradle.kts`; release still signed with the debug key, core-library desugaring on for `flutter_local_notifications`).
- `firebase deploy --only firestore:rules --project mediplan-35953` — no `.firebaserc`; must specify `--project`. `--only firestore:indexes` is a no-op (indexes live in Firebase console).
- `dart run flutter_launcher_icons` / `dart run flutter_native_splash:create` — regenerate the native launcher icon / splash after editing `assets/icon/` (config in `pubspec.yaml`; not covered by `flutter analyze`/`flutter test`). `icon.png` is for launcher/splash; `logo_app.png` is the in-app logo.

Toolchain: Flutter 3.47.2 / Dart 3.13.2 / firebase CLI 15.28.2 (pubspec pins `sdk: ^3.13.2`). Not a git repo; `firebase_options.dart` and `android/app/google-services.json` contain real populated keys for project `mediplan-35953` despite `firebase_options.dart`'s "PLACEHOLDER" header and the README — running `flutterfire configure` would overwrite working config.

## Critical Architecture

### Auth & Linking (vinculos)
- Caregiver/doctor: Firebase Auth (email/password or Google). Patient: anonymous `signInAnonymously()`; that UID is `dispositivoVinculadoId` on the paciente doc. **Never** write `LocalStore.getDispositivoId()` there (fails rules).
- Linking index: `vinculos/{MEDI-XXXXXX} = {pacienteId}`. Any authenticated user may `read` vinculos; writes require being the patient's `cuidadorId`. Codes normalized with `trim().toUpperCase()` everywhere (`buscarPacientePorCodigo`, `vincularDispositivoPorCodigo`, `desvincularDispositivo` index rewrite, `vincularPaciente`).
- Linking does **update-then-read** (without pre-reading paciente) to satisfy rules; if post-read fails, UI falls back to minimal `Paciente`. If you reintroduce read-before-write, this breaks. Caregiver code generation checks duplicates scoped to their `uid` via `buscarPacientePorCodigo` (+ `cuidadorId` filter) — design means same code reused by different caregivers can silently repoint `vinculos`.
- `AppState` only unlinks on definitive signals (doc gone, UID mismatch, `permission-denied`); network `unavailable` preserves local state. Patient cannot self-unlink (rules) — caregiver must call `FirestoreService.desvincularDispositivo` (sets `dispositivoVinculadoId = ''`).
- Provider gotcha: `AppState` provider is below root Navigator (only wraps `HomeRouter`). Routes pushed via `Navigator.push` don't see it; only `HomeRouter`'s direct children can `context.read/watch<AppState>()`. There's exactly one re-exposure in `seleccion_rol_screen.dart` for the patient branch.

### Alarms, Hashing, Notifications
- Deterministic alarm IDs: `NotificacionesService.idDeAlarma(tratamientoId, hora, dia) = hashEstable("$tratamientoId|$hora|$dia")` (31-bit polynomial, `0->1`), shared with `OmitidasService.idDocumento` (same recomputable property). `String.hashCode` not stable across runs. **Do not change `hashEstable`** — `test/notificaciones_service_test.dart` pins 5 literal IDs and asserts 63-collision freedom; `OmitidasService.idDocumento` has no such pins (add if touching hash).
- Back-compat cancellations: also cancels legacy `(id.hashCode ^ i) & 0x7FFFFFFF` and snooze id `(id.hashCode & 0x7FFFFFFF)+1`. Snooze uses `programarAlarmaDiaria` (one-shot) with id = `(tratamiento.id.hashCode & 0x7FFFFFFF)+1` (per-treatment constant) — not derived from `idDeAlarma`; second snooze overwrites. Never cancelled on "YA".
- `horarios.dias` fully wired (scheduling, cancellation, pending-dose detection). Scheduling registers one alarm per `(hora,dia)` with `dayOfWeekAndTime`. AlarmScreen auto-opens in `[now-5min,now+2min]` window (first match by document/horario order) with brightness boost/vibration; reconciliation suspended while open.
- Caregiver alerts: local notifications on `registrosToma` confirmations (`tomada|tardia|pospuesta`, one per registro) **and** `olvidó` — olvidadas aggregated into ONE summary notification per stream emission (`_procesarRegistros` in `dashboard_screen.dart`) so a multi-day reconciliation backfill doesn't spam. Shown only while the app is visible (`_appVisible()`); background/terminated coverage comes from FCM (next section). Testable pure logic lives in `push_service`'s helpers only if you add any.

### Push patient→caregiver (FCM HTTP v1, no Cloud Functions)
- `PushService` (`lib/services/push_service.dart`) sends from the **patient device** to `POST https://fcm.googleapis.com/v1/projects/mediplan-35953/messages:send` using `googleapis_auth` (`clientViaServiceAccount`, scope `firebase.messaging`, auto-refresh). **The service-account JSON ships inside the APK** (`assets/secrets/fcm_service_account.json`, gitignored; role should be limited to `cloudmessaging.messages.create`). It is trivially extractable — the real fix is a proxy server, not relocating the key.
- Caregiver token goes on `pacientes/{id}.cuidadorFcmToken` (NOT `usuarios/{uid}`): the anonymous patient device is the sender and rules don't let it read `usuarios`. **No rules change.** Written by the caregiver on dashboard open, on `onTokenRefresh`, and re-published whenever the dashboard's patient list changes (new patients are born without it); cleared via `FieldValue.delete()` on logout. Patient cannot clear a stale token (update rule), only the caregiver.
- Best-effort sending: `alarma_screen.dart` fires `unawaited(_push.notificarConfirmacion(...))` after the Firestore write (`_confirmar` and `_recordar`), and `AppState._reconciliarOmitidas` fires it for each `OmitidaNueva` written by the reconciliation (`EstadoToma.olvidada`, deduped per slot). `PushService` never throws, uses `.timeout(10s)`, and a missing credential disables push (`pushHabilitado`). While push is enabled, `DashboardScreen` suppresses its local notification when the app isn't visible (FCM shows it); without push, the local notification is the only path.
- Android: `firebase_messaging` is pinned to **15.x** on purpose (16.x needs `firebase_core` 4.x → forces auth/firestore majors). `POST_NOTIFICATIONS` already declared. FCM background/terminated notifications use channel `alertas_cuidador` (created in `NotificacionesService._crearCanales`, referenced by manifest `default_notification_channel_id`). No `<service>`/receiver declarations needed (plugin manifest merger). Foreground display is intentionally left to the Firestore listener.

### Missed-dose Reconciliation (`OmitidasService`)
- Pure/static enumeration (testable without Firebase); only `reconciliar()` is impure (reads Firestore) and now returns `List<OmitidaNueva>` (what it just wrote: idempotent thanks to the deterministic id + `resueltas`, so a slot only appears once per session). Slot expires when a strictly later slot exists at or before now across all treatments (intentional: same-hour meds don't expire each other; last slot of day never expires alone; `pospuesta` not terminal). 7-day backfill window. Idempotent via deterministic doc id `hashEstable('omitida|${ranura.clave}').toString()` written with `crearRegistroToma(idDoc:) -> .set()`; `firmaDe` fast-path + 5-min treatment cache. Driven by `AppState` on load/link, `AppLifecycleState.resumed` (forzar), and 60s timer; never throws. `AppState._reconciliarOmitidas` pushes each new `OmitidaNueva` to the caregiver (best-effort `unawaited`, deduped per slot in `_olvidadasAvisadas`).

## Data Model & Conventions
- Collections: `usuarios/{uid}`, `pacientes/{id}`, `vinculos/{codigo}`, `tratamientos/{id}`, `registrosToma/{id}` (no subcollections). Child docs carry parent ID.
- `estado` strings: `tomó|tardó|olvidó|pospuesta` (Spanish accented) via `EstadoTomaExt.nombre`; enum members differ (`tomada/tardia/olvidada/pospuesta`). Only non-`pendiente` states produced; `pendiente` never written. `tardó` if `now - horaProgramada > 15min` (strict). `esTerminal = tomada||tardia||olvidada`; `pospuesta` not terminal. The "Tomadas/Tardías/Olvidadas" counters in `detalle_paciente_screen.dart` compare the raw literals by hand, so a renamed/added state silently breaks them.
- Slot identity: `(tratamientoId, horaProgramada)`. Matching is exact instant — `omitidas_service`/`estadisticas` use millisecond granularity; patient UI uses minute-granular check. `horaProgramada` is local wall-clock `DateTime(y,m,d,H,M)` (no tz). Confirmations create new `registrosToma` docs.
- `tratamientos.frecuencia` and `duracion` are decorative only; scheduling/pending logic uses **only** `horarios`. `dosis` is `String` (guard on parse). `horarios` is `List<HorarioDia>` with `hora` "HH:mm" and `dias` (ISO 1=lunes..7=domingo); legacy `['HH:mm']` expands to all 7; empty explicit list respected; editor auto-fills empty selection to all 7.
- `resumen_horario.dart` returns positional `(String,String)` (call-site names matter). `estadisticas.dart` is pure (takes `ahora`), reuses `OmitidasService.ranurasDelDia` semantics. History labels in `etiqueta_toma.dart` compare calendar days (not 24h). Palette single-sourced in `lib/theme/app_colors.dart` (raw `Colors.*` only in alarm full-bleed). Base64 `fotoBase64` for images (no Storage).
- `pacientes/{id}.cuidadorFcmToken` (optional String): token FCM del cuidador espejado en el doc del paciente para que el dispositivo del paciente pueda enviarle el push (solo el cuidador lo escribe; sin el cambio de reglas). Puede faltar o estar vacío mientras el cuidador no haya abierto su app con permisos.

## Firestore Rules & API
- Single `firestore.rules` (73 lines). Helper functions must stay inside `match /databases/{database}/documents` scope. Query filters must prove the allow rule (e.g. caregiver lists filter by `cuidadorId`).
- `cloud_firestore` 5.6.x: `collection('x')` is `CollectionReference<Map<String,dynamic>>` (`.data()` already Map). `doc.get()` nullable → check `exists`, denied read throws `permission-denied`. New data access goes in `FirestoreService`; match existing style when editing mixed raw streams.
- Indexes: `firestore.indexes.json` empty; composites live in Firebase console only (not testable locally; `firebase deploy --only firestore:indexes` is a no-op). Exactly three `registrosToma` composites are required: `(pacienteId ASC, horaProgramada DESC)` shared by `streamRegistrosDePaciente`, `getRegistrosRecientes`, `streamRegistrosDePacientes` (`whereIn` counts as equality) and `_EstadoReciente` (`detalle_paciente_screen.dart`); `(pacienteId ASC, horaProgramada ASC)` for `getRegistrosEnRango` (reconcile; `FAILED_PRECONDITION` swallowed in `AppState`); `(pacienteId ASC, tratamientoId ASC, horaProgramada ASC)` for `streamTomasPendientesHoy`. Equality-only queries (`buscarPacientePorCodigo`, `streamPacientesDelCuidador`, `streamPacientePorDispositivo`, `streamTratamientosDePaciente`) need **no** composite — Firestore merges single-field indexes. Any new `where`/`orderBy` combination needs a console index or production-only `failed-precondition: The query requires an index`.

## Tests & Gotchas
- 7 files/77 tests, no Firebase init. Pure logic covered; `reconciliar()` not covered. Tests pin alarm hash literals — changing hash breaks them. `OmitidasService.idDocumento` has no pin (risky if hash changes).
- Firestore-dependent flows are verified **only manually**: README's "Prueba del flujo completo" is the current end-to-end script (needs two devices/emulators or the Firestore console).
- Alarm brightness: `SensoresService.subirBrilloAlMaximo()` requires `WRITE_SETTINGS`; it checks `canChangeSystemBrightness`, opens the special settings page once (`asegurarPermisoBrillo`), and saves the prior system brightness so `restaurarBrillo()` restores it. `screen_brightness` 2.1.11 has no `resetSystemScreenBrightness`, hence the manual save; alarm re-raises on resume.
- Live bug to know: AndroidManifest declares no `<receiver>` components (ScheduledNotificationReceiver/BootReceiver/ActionBroadcastReceiver) — only permissions, incl. `RECEIVE_BOOT_COMPLETED`; the plugin's own manifest adds none, so scheduled alarms don't survive reboot and action buttons aren't handled. `flutter analyze` cannot catch this.
- Dead code exists (e.g. `LocalStore.getDispositivoId()`, some old vinculation methods) — don't "fix" them blindly; read comments/symbols first. `usuarios` written only on register/Google (not email/password) if doc doesn't exist.
